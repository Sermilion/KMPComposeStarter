## [2026-08-29] KMP-1 subtask 3 (completion pass) — terminal delete-my-data contract
Areas: core/data (db, repository), feature/profile, docs/architecture
- The whole behavioral change is one operator: `ProfileViewModel`'s `observeCurrentUser()` collector gained a `.catch` that logs and stops following the stored row. Without it a delete that closed the database and then failed to unlink the files left the collector throwing into `viewModelScope` and taking the session down. Net 5 files, +43/-6; the other four are contract text.
- Reusable rule this pass settled: a delete-my-data path that must close the DB before unlinking its files is **terminal whichever way it returns**. Room hands out one instance and a closed one cannot be un-closed, so a `false` is not retryable into a working handle. Model such a call as "session stays signed in, reports the failure, and can no longer read its own row" — never as recoverable, and never as a reason to sign the user out.
- Considered and rejected: making the handle recoverable. That needs re-plumbing `StarterUserDao`'s database resolution and re-establishing the Room flow after a failed delete — larger than the gap it closes — and close-before-delete is mandatory on all three platforms (unlinking a file an open connection holds either fails outright or leaves that connection writing to an orphaned inode).
- The contract is now stated at every site that carries it: `DatabaseProvider.deleteDatabaseForUser` KDoc, the close call in `StarterRoomDatabaseProvider`, `StarterUserRepository.deleteMyData` KDoc, `ProfileViewModel.deleteMyData` KDoc, and `docs/architecture/persistence.md`. Reusable: a contract spread across a provider → repository → ViewModel chain goes stale unless each link restates it; one KDoc at the interface is not enough.
- Deliberately no new test: a deterministic file-deletion failure is not reproducible on the JVM host without mocking the platform builder factory, and the `.catch` does not change `ProfileViewModelTest`'s observable contract (stays signed in, reports failure, never logs out), so the existing test needed no update either.
- Known limitation and review watch: the `.catch` is untyped, so any upstream repository error — not only a post-delete read failure — degrades to a stale profile plus one Kermit warning instead of a visible error. Acceptable for a starter with one failure mode on this flow; a fork that adds more should narrow it.
- Validate risk carried forward from subtask 2: the KSP `dependsOn(generateNetworkConfig)` ordering is still inspection-reasoned, not compile-proven — an unresolved `NetworkConfig` on any target has that as its named cause, not a flake. ~85 branch files have not passed spotless/detekt, so formatting churn on the first gate run is expected rather than a defect signal.
